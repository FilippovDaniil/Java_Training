# Модуль 122. Контракты событий: конверт, схемы, совместимость, заголовки, имена топиков

Продюсер пишет ([модуль 120](../m120_kafka_producer_spring/theory.md)), консьюмер читает ([модуль 121](../m121_kafka_consumer_spring/theory.md)) — пока оба в одном учебном проекте. В продукте у события **много подписчиков в разных сервисах и командах**, а топик хранит записи неделями. Значит, событие — это **публичный контракт**, который нельзя менять произвольно: старые сообщения в логе должны читаться новым кодом, а старый код — не падать на новых сообщениях.

Модуль про то, как этот контракт спроектировать: конверт события, выбор формата (JSON / Avro / Protobuf), Schema Registry и правила совместимости, заголовки сообщений, соглашения об именовании топиков и версионирование.

> Практика — задачи в `practice/`. Формат смешанный: **Spring-код** (конверт, заголовки, эволюция схемы, `type.mapping`) и **носители артефактов** (`.avsc`-схема, конфиг Schema Registry, разбор совместимости). Сквозной проект — контракт событий **Task Tracker v1 → v2**.

## Событие как контракт: конверт + полезная нагрузка

```
   Сообщение Kafka
   +---------------------------------------------------------------+
   | key: "42"                     (идентификатор сущности)         |
   | headers: eventId, eventType, version, traceId, source          |
   | value:  { "eventId": "...", "type": "task.created", "version": 1,
   |           "occurredAt": "...", "payload": { ... } }             |
   +---------------------------------------------------------------+
```

| Поле конверта | Зачем |
|---------------|-------|
| `eventId` (UUID) | **дедупликация** у потребителя (at-least-once — модуль 123) |
| `type` | что произошло: `task.created`, `task.status.changed` |
| `version` | версия схемы полезной нагрузки |
| `occurredAt` | когда произошло **в домене** (не когда отправлено) |
| `traceId` / `correlationId` | сквозная трассировка через сервисы |
| `source` | сервис-источник (для аудита) |
| `payload` | собственно данные события |

```java
public record EventEnvelope<T>(
        UUID eventId,
        String type,
        int version,
        Instant occurredAt,
        String traceId,
        String source,
        T payload) { }
```

> Минимум, без которого потом больно: **`eventId`** (иначе нечем дедуплицировать), **`occurredAt`** (иначе неясен порядок в домене) и **`version`** (иначе непонятно, как читать `payload`).

## Что кладут в `payload`: три стиля

| Стиль | Что внутри | Плюсы | Минусы |
|-------|-----------|-------|--------|
| **Event notification** | только идентификаторы: `{"taskId": 42}` | минимальный контракт | подписчик идёт за данными по REST → связанность и нагрузка |
| **Event-carried state transfer** | нужные поля состояния: `{"taskId":42,"title":"...","status":"DONE"}` | подписчик автономен | контракт шире, риск устаревших данных |
| **Delta / состояние «было → стало»** | `{"old":"NEW","new":"DONE"}` | видно сам переход | нужен аккуратный порядок |

На практике для внутренних событий берут **state transfer с достаточным набором полей** — так подписчик не бомбардирует источник запросами. Подробнее о выборе — [модуль 124](../m124_kafka_event_patterns/theory.md).

**Никогда не публикуйте JPA-сущность.** Событие — отдельный `record`, чья схема меняется по правилам совместимости, а не вслед за миграциями БД.

## Формат: JSON, Avro, Protobuf

| Критерий | JSON | Avro | Protobuf |
|----------|------|------|----------|
| Читается глазами в CLI | да | нет (бинарь) | нет |
| Размер | большой | компактный | компактный |
| Схема | «в договорённостях»/JSON Schema | `.avsc`, обязательна | `.proto`, обязательна |
| Контроль совместимости | вручную/через Registry + JSON Schema | Registry проверяет автоматически | Registry проверяет автоматически |
| Кодогенерация | не нужна | `avro-maven/gradle-plugin` | `protoc` |
| Порог входа | низкий | средний | средний |
| Когда выбирать | внутренние события, старт проекта, немного подписчиков | много подписчиков/команд, важна строгость и объём | межъязыковые API, gRPC уже в стеке |

Практичный путь: **начать с JSON + дисциплина в правилах эволюции**, перейти на Avro/Protobuf, когда подписчиков стало много и «договорённости» перестали работать.

## Schema Registry: как это работает

```
   PRODUCER                                REGISTRY                       CONSUMER
   value -> схема зарегистрирована?  ---->  subject: task.created-value
                                            v1, v2 ... + правило совместимости
        <---- schema id = 7 -----------------
   в сообщение: [0x00][schema id 7][бинарные данные]  ---->  читает id 7,
                                                             берёт схему из Registry,
                                                             десериализует
```

| Понятие | Смысл |
|---------|-------|
| **subject** | единица версионирования; по умолчанию `<топик>-value` и `<топик>-key` |
| **schema id** | ссылка на схему, зашитая в первые байты сообщения (magic byte + 4 байта) |
| **compatibility level** | правило, по которому Registry принимает или отвергает новую версию |

```yaml
# конфигурация клиента (Confluent-стек)
spring:
  kafka:
    producer:
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
      properties:
        schema.registry.url: http://schema-registry:8081
        auto.register.schemas: false      # на проде схемы регистрирует CI, а не приложение
```

> Registry — отдельный сервис (в Compose добавляется рядом с брокером). Без него Avro тоже работает, но схему придётся раздавать вместе с кодом — теряется главный смысл.

## Совместимость схем: четыре режима

```
   BACKWARD: новый КОД читает старые данные   (сначала обновляем потребителей)
   FORWARD:  старый КОД читает новые данные   (сначала обновляем производителей)
   FULL:     и то, и другое
   NONE:     проверок нет (так делать нельзя)
```

| Изменение | BACKWARD | FORWARD |
|-----------|----------|---------|
| Добавить поле **с дефолтом** | совместимо | совместимо |
| Добавить обязательное поле без дефолта | **нет** | да |
| Удалить поле с дефолтом | совместимо | совместимо |
| Удалить обязательное поле | да | **нет** |
| Переименовать поле | **нет** (это удаление + добавление) | **нет** |
| Сменить тип (`int` → `long`, `string` → `int`) | обычно **нет** | обычно **нет** |
| Добавить значение в `enum` | зависит от дефолта | **нет** |

**Практические правила эволюции контракта:**

1. Поля только **добавляются**, и всегда с дефолтом/nullable.
2. Ничего не переименовывается и не меняет тип — при необходимости добавляется новое поле, старое живёт до отмирания.
3. Потребители **игнорируют неизвестные поля** (Jackson: `FAIL_ON_UNKNOWN_PROPERTIES=false`).
4. Смысл существующего поля не меняется (это самая опасная «незаметная» несовместимость: тип тот же, а данные другие).
5. Ломающее изменение — **новый топик/новая major-версия**: `task.created.v2` (и период двойной публикации).

```
   Ломающее изменение — миграция:
   producer -> task.created.v1 (старые подписчики)
            -> task.created.v2 (новые подписчики)     двойная публикация
   ... все подписчики переехали на v2 ...
   -> публикация v1 прекращается, топик доживает retention и удаляется
```

## Заголовки сообщений

```java
ProducerRecord<String, Object> record = new ProducerRecord<>("task.created", key, payload);
record.headers().add("eventId", eventId.toString().getBytes(UTF_8));
record.headers().add("eventType", "task.created".getBytes(UTF_8));
record.headers().add("traceId", traceId.getBytes(UTF_8));
kafka.send(record);
```

```java
@KafkaListener(topics = "task.created", groupId = "notifier")
public void on(TaskCreated payload,
               @Header("eventId") String eventId,
               @Header(KafkaHeaders.RECEIVED_KEY) String key) { ... }
```

| В заголовки | В `value` |
|-------------|-----------|
| техническая метаинформация: `eventId`, `traceId`, `eventType`, версия схемы | бизнес-данные события |
| то, что нужно посреднику **без разбора тела** (маршрутизация, фильтрация, DLQ-диагностика) | то, что описано схемой |

Spring сам добавляет служебные заголовки: `__TypeId__` (`JsonSerializer`), `kafka_dlt-*` (при публикации в DLQ), `spring.deserializer.*` (при сбое десериализации). Их видно в `kafka-ui` и в `kafka-console-consumer.sh --property print.headers=true`.

## Имена топиков и групп

```
   <домен>.<сущность>.<событие>[.vN]        task.created · billing.invoice.paid · task.created.v2
```

| Правило | Пример |
|---------|--------|
| Только имена **произошедшего**, в прошедшем времени | `task.created`, не `create.task` |
| Разделитель — точка, нижний регистр | `billing.invoice.paid` |
| Разделять **внутренние** и **публичные** контракты префиксом | `inner.*` (только для наших сервисов) / `exchange.*` (наружу, менять нельзя) |
| Версия — суффиксом, только при ломающем изменении | `task.created.v2` |
| `group.id` = **потребитель + назначение** | `notifier`, `analytics`, `search-indexer` |
| Топик DLQ — от исходного | `task.created.DLT` |

> Разделение `inner.*` / `exchange.*` — правило из моей рабочей практики (см. `~/.claude/CLAUDE.md`): контракты `exchange.*` считаются публичными и меняются только совместимо, `inner.*` можно менять быстрее по согласованию внутри команды.

## Документирование контракта

| Инструмент | Что даёт |
|------------|----------|
| **AsyncAPI** | спецификация асинхронного API (аналог OpenAPI): топики, схемы, примеры |
| Schema Registry | схемы как источник правды + история версий |
| `.avsc` / `.proto` в общем репозитории | ревью изменений контракта через pull request |
| README/ADR | почему выбран стиль события, кто подписчики, как версионируется |

Минимальный порядок в команде: изменение контракта = pull request со схемой + версией + указанием влияния на подписчиков.

## Подводные камни

| Проблема | Причина | Решение |
|----------|---------|---------|
| Подписчики падают после релиза | добавили обязательное поле / переименовали | только совместимые изменения, дефолты, `FAIL_ON_UNKNOWN_PROPERTIES=false` |
| «У нас же JSON, схемы не нужны» — сломались через месяц | нет проверки совместимости | JSON Schema в Registry или строгие правила ревью контракта |
| `The class ... is not in the trusted packages` | `JsonDeserializer` не доверяет типу из `__TypeId__` | `spring.json.trusted.packages` или `type.mapping` |
| Потребитель на другом языке не может разобрать | `__TypeId__` с Java-классом | `ADD_TYPE_INFO_HEADERS=false` + `spring.json.type.mapping` |
| Дубли обрабатываются как новые события | в событии нет `eventId` | конверт с `eventId`, дедупликация у потребителя |
| Порядок событий восстановить нельзя | нет `occurredAt`, только время брокера | `occurredAt` в конверте (UTC, `Instant`) |
| Топик распух в разы | JSON + отсутствие сжатия | `compression.type=lz4`, при объёме — Avro/Protobuf |
| Publish/subscribe превратился в REST-звонки | стиль «только id» + подписчик дочитывает данные | добавить нужные поля в событие (state transfer) |
| Ломающее изменение «протащили» в тот же топик | нет процесса версионирования | новый топик `.v2` + двойная публикация + план вывода v1 |
