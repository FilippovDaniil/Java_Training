## Проблема двойной записи

```
   @Transactional
   void createTask(...) {
       repository.save(task);            // 1. запись в БД
       kafka.send("task.created", ...);  // 2. отправка в брокер
   }                                     // <- коммит транзакции БД

   Сбой между 1 и 2:  БД зафиксировала, события нет   -> подписчики не узнали (потеря)
   Сбой после 2, откат транзакции: события ушли       -> подписчики знают о небывшем (фантом)
```

Два разных хранилища невозможно закоммитить атомарно без распределённой транзакции (XA — дорого, хрупко, в Kafka не поддерживается). Правильное решение — **outbox**.

## Outbox pattern

Событие пишется **в ту же БД, той же транзакцией**, что и бизнес-данные. Отправкой в Kafka занимается отдельный процесс.

```
   ТРАНЗАКЦИЯ БД                                    ОТДЕЛЬНО (релэй)
   +----------------------------+                   +-------------------------+
   | INSERT INTO tasks ...      |                   | SELECT * FROM outbox    |
   | INSERT INTO outbox(...)    |    ---------->    | WHERE sent_at IS NULL   |
   +----------------------------+                   | -> send в Kafka         |
        атомарно: либо оба, либо ничего             | -> UPDATE sent_at=now() |
                                                    +-------------------------+
```

```sql
CREATE TABLE outbox (
    id           uuid PRIMARY KEY,          -- он же eventId для дедупликации
    aggregate_id varchar(64) NOT NULL,      -- ключ сообщения (id задачи)
    topic        varchar(128) NOT NULL,
    type         varchar(64)  NOT NULL,
    payload      jsonb        NOT NULL,
    occurred_at  timestamptz  NOT NULL,
    sent_at      timestamptz,               -- NULL = ещё не отправлено
    attempts     int NOT NULL DEFAULT 0
);
CREATE INDEX outbox_unsent_idx ON outbox (occurred_at) WHERE sent_at IS NULL;
```

```java
@Transactional
public void createTask(CreateTask cmd) {
    Task task = repository.save(new Task(cmd.title()));
    outbox.save(OutboxMessage.of("task.created", task.getId(), new TaskCreated(...)));  // та же транзакция
}

// релэй: отдельный поток/под, работает независимо от HTTP-запросов
@Scheduled(fixedDelay = 500)
@Transactional
public void publishBatch() {
    for (OutboxMessage m : outbox.findUnsent(100)) {         // SELECT ... FOR UPDATE SKIP LOCKED
        kafka.send(m.topic(), m.aggregateId(), m.payload())
             .whenComplete((r, ex) -> { if (ex == null) outbox.markSent(m.id()); });
    }
}
```

| Деталь | Как правильно |
|--------|---------------|
| Гарантия | at-least-once: релэй может отправить дважды → потребитель идемпотентен (модуль 123) |
| Конкуренция реплик | `SELECT ... FOR UPDATE SKIP LOCKED` — две реплики не возьмут одну строку |
| Порядок | сортировка по `occurred_at`/`id`; ключ = `aggregate_id` → порядок в партиции |
| Очистка | удалять отправленные старше N дней (иначе таблица растёт) |
| Альтернатива релэю | **CDC**: Debezium читает WAL и публикует строки outbox сам |
| Что НЕ делать | отправлять в Kafka из `@Transactional`-метода и надеяться на лучшее |

> `@TransactionalEventListener(phase = AFTER_COMMIT)` — упрощённый вариант: событие публикуется после коммита. Он закрывает «фантомы», но не потери: если брокер недоступен сразу после коммита, событие исчезнет. Для важных событий — outbox.

## CDC: Change Data Capture (Debezium)

```
   PostgreSQL ---WAL---> Debezium Connect ---> Kafka topic (по таблице)
   (никаких правок в коде приложения)
```

| Плюсы | Минусы |
|-------|--------|
| Не нужно менять приложение | В топик уходят **строки таблиц**, а не бизнес-события |
| Ничего не теряется (журнал БД — источник правды) | Схема БД становится публичным контрактом |
| Хорошо для репликации/аналитики/поиска | Потребителю нужно самому собирать смысл из строк |

Практика: CDC применяют **вместе** с outbox — Debezium читает не бизнес-таблицы, а таблицу `outbox` (Debezium Outbox Event Router). Тогда контракт остаётся событийным, а релэй писать не нужно.

## Стили событий: notification / state transfer / event sourcing

| Стиль | Что в событии | Кто хранит правду | Когда |
|-------|---------------|-------------------|-------|
| **Event notification** | «задача 42 изменилась» | источник (БД сервиса) | минимальная связанность, подписчик дочитает по API |
| **Event-carried state transfer** | текущее состояние задачи | источник | подписчику нужны данные без обратных вызовов (частый выбор) |
| **Event sourcing** | все изменения как последовательность фактов | **сам лог событий** | нужна полная история, аудит, восстановление состояния на любой момент |

```
   Event sourcing:
   события:  TaskCreated -> TaskAssigned -> TaskDone
                    |
             replay (свёртка)  ->  текущее состояние задачи
             snapshot каждые N событий  ->  чтобы не проигрывать всё с нуля
```

Event sourcing даёт аудит и «машину времени», но требует зрелости: миграции старых событий, снапшоты, отдельная модель чтения. **Kafka-топик — не база данных для запросов:** по нему нельзя «выбрать все задачи в статусе DONE». Для чтения строят проекции.

## CQRS-проекции

```
   команды (запись)                                   запросы (чтение)
   REST -> TaskService -> БД задач                     REST -> DashboardRepository
                            |                                     ▲
                            +-- события -> Kafka -> projector ----+
                                                    (materialized view: своя таблица/индекс)
```

| Свойство | Следствие |
|----------|-----------|
| Модель чтения оптимизирована под экран/отчёт | быстрые запросы без джойнов |
| Проекция **eventually consistent** | UI может увидеть данные с задержкой — это нужно проектировать явно |
| Проекция восстанавливаема | перечитали топик с начала → пересобрали таблицу (для этого нужен retention/compaction) |
| Проектор идемпотентен | upsert по ключу + проверка версии события |

Типичные проекции: дашборд, поисковый индекс (OpenSearch/Elasticsearch), аналитическая витрина, кэш в Redis.

## Saga: распределённый процесс без общей транзакции

```
   ХОРЕОГРАФИЯ (сервисы слушают события друг друга)
   OrderCreated -> [payment] PaymentAuthorized -> [warehouse] StockReserved -> [delivery] ...
        сбой на шаге N -> компенсирующее событие: PaymentRefunded, StockReleased

   ОРКЕСТРАЦИЯ (координатор ведёт процесс)
   Orchestrator: команда -> ждёт ответ -> следующая команда; при сбое -> компенсации
```

| | Хореография | Оркестрация |
|---|---|---|
| Логика процесса | размазана по сервисам | в одном координаторе |
| Связанность | ниже | выше (координатор знает всех) |
| Наблюдаемость процесса | сложнее (нужна трассировка) | проще (есть состояние саги) |
| Когда | 2–3 шага, простые компенсации | 4+ шага, сложные откаты, таймауты |

Ключевые требования к любой саге: **каждый шаг идемпотентен**, **у каждого шага есть компенсация**, **есть таймауты** и **состояние процесса где-то хранится** (иначе после рестарта непонятно, где вы находитесь).

## Compacted-топики как «таблица состояний»

```
   cleanup.policy=compact, ключ = id сущности
   task.state:  key=42 -> {status: NEW} ... key=42 -> {status: DONE}
                                 |
                  compaction оставляет ПОСЛЕДНЕЕ значение на ключ
                  key=42 -> null (tombstone) = «сущность удалена»
```

Применение: снимок текущего состояния, который новый сервис читает целиком при старте (bootstrap), конфигурация, справочники, «таблица» для `KTable` в Kafka Streams.

| Правило | Почему |
|---------|--------|
| Ключ обязателен | compaction работает по ключу |
| Отдельный топик от потока событий | поток фактов (`task.created`) и снимок состояния (`task.state`) — разные вещи |
| `null` = tombstone | не «пустое значение», а удаление ключа |
| Не средство «удалить старьё» | для этого `retention.ms` |

## Kafka Streams / ksqlDB — коротко

| Инструмент | Для чего |
|------------|----------|
| **Kafka Streams** | библиотека для обработки потоков в вашем Java-приложении: `map`/`filter`/`join`/`groupBy`/оконные агрегации, состояние в RocksDB, exactly-once (`processing.guarantee=exactly_once_v2`) |
| **ksqlDB** | SQL-подобный язык над теми же возможностями (без Java-кода) |
| **Kafka Connect** | готовые коннекторы source/sink (БД, S3, OpenSearch) без своего кода |

Когда достаточно `@KafkaListener`: простая обработка «событие → эффект в БД/внешний вызов». Когда нужен Streams: агрегации по окнам, join потоков, материализованные состояния с гарантиями.

## Как выбирать паттерн

```
   Нужна атомарность «БД + событие»?           -> outbox (+ CDC, если не хочется релэя)
   Нужно быстро читать по-другому?             -> CQRS-проекция
   Нужен процесс через несколько сервисов?     -> saga (2-3 шага: хореография, больше: оркестрация)
   Нужна полная история/аудит/машина времени?  -> event sourcing (осознанно, это дорого)
   Нужен «снимок состояния» для новых сервисов?-> compacted-топик
   Нужны агрегации/окна/join потоков?          -> Kafka Streams
```

## Подводные камни

| Проблема | Причина | Решение |
|----------|---------|---------|
| «Событие ушло, а в БД ничего нет» | публикация внутри транзакции | outbox (или как минимум `AFTER_COMMIT`) |
| Outbox отправляет дубли | релэй упал между send и `markSent` | это норма для at-least-once → идемпотентный потребитель |
| Две реплики релэя отправляют одно событие дважды | нет блокировки строк | `FOR UPDATE SKIP LOCKED` |
| Таблица outbox распухла до миллионов строк | нет очистки отправленных | периодическое удаление старше N дней |
| Проекция «разъехалась» с источником | потерянные/переупорядоченные события, неидемпотентный проектор | upsert + версия события + возможность пересборки с начала топика |
| Пересобрать проекцию нельзя | события уже удалены по retention | увеличить retention / compaction / хранить снапшоты |
| Сага «подвисла» | нет таймаутов и состояния процесса | таблица состояний саги + таймауты + компенсации |
| Компенсация выполнилась дважды | шаг компенсации не идемпотентен | тот же `eventId`-подход, что и в обработчиках |
| Из Kafka пытаются делать запросы «где статус=DONE» | лог принят за БД | проекция в БД/поисковый индекс |
| CDC сделал схему БД публичным контрактом | Debezium читает бизнес-таблицы | Debezium + таблица outbox (Outbox Event Router) |
